## 5. Semantic Architecture

`SEMANTIC.TRUSTED_BANKING_OPERATIONS` is one coherent Snowflake Semantic View for the lighthouse. Its five logical tables are deliberately disconnected. Their grains cannot be safely joined without multiplying measures, and no relationship is needed for the approved questions. Queries therefore use one logical table at a time.

## 9. Relationships

No cross-table relationship is declared in version 1.0.0. This is a deliberate preventive control against fanout, many-to-many ambiguity, aggregate-to-detail joins, and measure multiplication. A future relationship requires new evidence, approval, regression tests, and a semantic version change.

## 10. Dimensions

Approved dimensions cover business/event date, period, exception ID for controlled drilldown, payment ID, reason, status, resolution, channel, currency, high-value flag, SLA breach, escalation requirement, priority and explanation, team, and synthetic context. Workload and SLA expose only their necessary domain dimensions.

## 11. Measures

The model exposes governed payment, exception, high-value payment, high-value exception, unresolved exception, SLA breach, escalation, workload, case, and resolved-workload measures. Payment amount and breach minutes are facts at their documented case grains.

## 12. Metric Definitions

The ten `GOVERNANCE.GOLD_METRIC_CATALOG` definitions map through `GOVERNANCE.SEMANTIC_METRIC_MAPPING`. Ratios are recomputed from additive components and return `NULL` for a zero denominator.

`HIGH_VALUE_EXCEPTION_RATE = HIGH_VALUE_EXCEPTION_COUNT / NULLIF(HIGH_VALUE_PAYMENT_COUNT, 0)`.

It means the percentage of high-value payments that became trusted exceptions. It is never high-value exceptions divided by all exceptions. No precomputed rate is averaged.

No FX model exists. Monetary facts must retain currency, and no cross-currency single total is meaningful or approved.

Period windows overlap. Always filter or group period metrics by `period`; never sum investigation week, previous week, trailing four weeks, and historical baseline together.

## 13. Synonyms and Business Descriptions

Controlled synonyms cover payment exception/exception case, high-value payment/large payment, SLA breach/SLA violation, and operations team/operations owner. Descriptions state meaning, grain, source, and prohibited inference without mapping one term to conflicting concepts.

## 14. Sensitive-Data Minimization

The model does not expose names, date of birth, email, phone, address, raw account/customer identifiers, beneficiary detail, assigned-user identity, or even Gold's minimized customer/account/user hashes. Exception ID and payment ID are retained only for authorized operational drilldown, including `EXC_DEMO_001`.

## 15. Semantic Governance Registry

The registry captures identity, domain, owner, steward, purpose, lifecycle, version, eligibility, context-admission requirement, certification intent, effective time, limitations, requirements, and control families. Separate tables capture the five Gold dependencies and ten metric mappings without creating a parallel metadata platform.

## 16. Semantic Versioning

Version `1.0.0` is the initial contract. A material change to metric meaning, grain, relationship, allowed dimension, purpose, or sensitivity requires deliberate impact review, regression evidence, approval, and a new semantic version.

## 17. Certification Lifecycle

The lifecycle is `DRAFT` → `READY_FOR_EXECUTION` → `APPROVED` → `RETIRED`. Certification is separate: `NOT_CERTIFIED` → `READY_FOR_CERTIFICATION` → `CERTIFIED`, or `REJECTED`. G3.1 prepares execution; only successful runtime deployment and validation may advance certification.

## 18. Semantic Access Control

`TRUSTED_AI_SEMANTIC_CONSUMER` receives explicit `USAGE` on `COMPUTE_WH`, database/schema usage, plus `SELECT` and `REFERENCES` on the Semantic View, and no direct Gold access. Warehouse usage is the least-privilege compute dependency for governed Semantic View query execution; it does not grant `OPERATE`, `MODIFY`, `MONITOR`, or ownership. `SELECT` queries the Semantic View; `REFERENCES` supports structure inspection and future Cortex Analyst use. Steward and auditor receive approved structure/registry evidence, not semantic business results. Bronze reader and tag administrator receive no semantic access.

Semantic View authorization is independent of Gold RBAC. Applicable source masking and row-access policies remain enforceable. Current Snowflake execution behavior and future Cortex Analyst execution-role dependencies must be revalidated before any additional underlying access is considered.

## 25. Demo SQL and Query Examples

These read-only examples are for later execution and do not invoke Cortex Analyst.

```sql
-- 1. Investigation-week high-value exception rate.
SELECT * FROM SEMANTIC_VIEW(
  TRUSTED_AI_GOVERNANCE.SEMANTIC.TRUSTED_BANKING_OPERATIONS
  DIMENSIONS period_comparison.period
  METRICS period_comparison.high_value_payment_count,
          period_comparison.high_value_exception_count,
          period_comparison.high_value_exception_rate
  WHERE period_comparison.period='INVESTIGATION_WEEK');

-- 2. Investigation-week versus previous-week comparison.
SELECT * FROM SEMANTIC_VIEW(
  TRUSTED_AI_GOVERNANCE.SEMANTIC.TRUSTED_BANKING_OPERATIONS
  DIMENSIONS period_comparison.period
  METRICS period_comparison.exception_count,period_comparison.payment_count,
          period_comparison.exception_rate,period_comparison.high_value_exception_rate
  WHERE period_comparison.period IN ('INVESTIGATION_WEEK','PREVIOUS_WEEK'));

-- 3. Top investigation-week exception reasons.
SELECT * FROM SEMANTIC_VIEW(
  TRUSTED_AI_GOVERNANCE.SEMANTIC.TRUSTED_BANKING_OPERATIONS
  DIMENSIONS investigation.exception_reason
  METRICS investigation.exception_case_count
  WHERE investigation.primary_period='INVESTIGATION_WEEK');

-- 4. SLA breached cases by priority and team.
SELECT * FROM SEMANTIC_VIEW(
  TRUSTED_AI_GOVERNANCE.SEMANTIC.TRUSTED_BANKING_OPERATIONS
  DIMENSIONS sla_exposure.priority,sla_exposure.team
  METRICS sla_exposure.sla_case_count,sla_exposure.sla_breach_count
  WHERE sla_exposure.sla_breached);

-- 5. Workload by operations team.
SELECT * FROM SEMANTIC_VIEW(
  TRUSTED_AI_GOVERNANCE.SEMANTIC.TRUSTED_BANKING_OPERATIONS
  DIMENSIONS workload.team
  METRICS workload.open_exception_count,workload.high_value_open_count,
          workload.sla_breach_open_count,workload.escalation_required_open_count);

-- 6. Governed investigation semantics for EXC_DEMO_001.
SELECT * FROM SEMANTIC_VIEW(
  TRUSTED_AI_GOVERNANCE.SEMANTIC.TRUSTED_BANKING_OPERATIONS
  DIMENSIONS investigation.exception_id,investigation.payment_id,
             investigation.exception_reason,investigation.priority,
             investigation.priority_reason,investigation.high_value,
             investigation.sla_breached,investigation.team
  WHERE investigation.exception_id='EXC_DEMO_001');
```
