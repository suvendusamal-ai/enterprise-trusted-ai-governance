# G2.3 — Governed Bronze Ingestion Runbook

## 1. Purpose

This runbook deploys and demonstrates the first physical Snowflake foundation for the Trusted Banking Operations AI lighthouse. **Governance begins at Bronze**: raw synthetic source values enter a restricted layer with source identity, file and row provenance, one ingestion-run correlation context, classification intent, project tags, and load evidence.

Bronze preserves source meaning and deliberate defects. It does not standardize, derive, correct, quarantine, or certify records; those are later Silver responsibilities.

## 2. Prerequisites

- An intended non-production Snowflake development/lighthouse account.
- A deployment administrator able to create a database, schemas, roles, grants, tags, stages, file formats, tables, and—when available—a classification profile.
- SnowSQL, Snowflake CLI, Snowsight, or an equivalent approved SQL client.
- The approved G2.2 files under `<REPOSITORY_ROOT>/data/synthetic/source/`.
- A warehouse selected by the deployer; warehouse creation and sizing are outside G2.3.
- Enterprise Edition or higher for sensitive-data classification and `ACCOUNT_USAGE.ACCESS_HISTORY`. Project tags and ingestion evidence do not depend on these edition features.
- Awareness that automatic classification can begin roughly one hour after profile assignment and Access History can have approximately three hours of latency.

Do not place passwords, tokens, private keys, connection strings, or account/user identifiers in repository files. User-to-role assignment and authentication remain deployment-specific.

### Native-classification capability gate

**Step A — determine capability.** Verify the account edition through an approved read-only account metadata mechanism and check whether `SNOWFLAKE.DATA_PRIVACY.CLASSIFICATION_PROFILE` is exposed. Do not infer availability merely because the `SNOWFLAKE.CLASSIFICATION_ADMIN` database role is visible.

**Step B — feature available.** Execute only the three statements under `OPTIONAL NATIVE CLASSIFICATION — ENTERPRISE EDITION OR HIGHER` in `042_bronze_access_controls.sql`, then execute `043_bronze_classification_setup.sql`. Record the native result as executed or pending; asynchronous delay is not a failure.

**Step C — feature unavailable.** Do not execute the optional grants or `043_bronze_classification_setup.sql`. Record exactly:

`NATIVE CLASSIFICATION: NOT AVAILABLE IN CURRENT ACCOUNT/EDITION`

Continue with source upload and Bronze ingestion. Native classification is additive evidence, not the sole Bronze classification control. The seven project tags, including `DATA_CLASSIFICATION`, `SENSITIVITY_LEVEL`, `DATA_LAYER`, and `SYNTHETIC_DATA`, remain mandatory.

## 7. Governance Proof

Demonstrate the chain:

**Source File → Named Internal Stage → Bronze Row → Source Metadata → Project Tag → Restricted Access → Ingestion Evidence → Native Audit/Access Evidence**

1. `LIST` the staged path and identify the source file.
2. Query an anchor row and show `_SOURCE_ID`, `_SOURCE_FILE_NAME`, `_SOURCE_FILE_ROW_NUMBER`, `_SOURCE_FILE_CONTENT_KEY`, `_STAGE_SCAN_TIME`, `_INGESTION_RUN_ID`, and `_INGESTED_AT`.
3. Use `SYSTEM$GET_TAG` or `TAG_REFERENCES_ALL_COLUMNS` to show `DATA_LAYER`, `SYNTHETIC_DATA`, domain, purpose, classification, and sensitivity.
4. Demonstrate an allowed read with `TRUSTED_AI_BRONZE_READER` and capture separately authorized denial evidence for out-of-scope writes/metadata.
5. Join the row's `_INGESTION_RUN_ID` to `AUDIT.INGESTION_RUN` and `AUDIT.INGESTION_FILE_EVIDENCE`.
6. Later, correlate the COPY query through `SNOWFLAKE.ACCOUNT_USAGE.ACCESS_HISTORY` when edition and latency permit.

## 8. Negative Proof

Bronze governance does not mean silently repairing source data. Run `test_bronze_source_preservation.sql` to show:

- `PAY_DQ_NEGATIVE_001` retains `payment_amount = -1250.00`.
- `PAY_DQ_CURRENCY_001` retains `currency_code = ZZZ`.
- `EXC_DQ_TIMESTAMP_001` retains an exception timestamp before its payment.
- `EXC_DQ_REASON_001` retains the missing reason value as `NULL` under the documented CSV empty-field rule.
- `EXC_DQ_EXPIRED_REF_001` retains expired reference code `R_EXP`.
- `SLA_DQ_DUE_001` retains a due timestamp before the SLA start.

Each remains correlated to file and run metadata. Silver validation and quarantine are not implemented here.

## 9. Classification Proof

Two complementary proofs exist:

- **Project-defined classification:** synchronous governed tag assignments such as `DATA_CLASSIFICATION`, `SENSITIVITY_LEVEL`, `DATA_DOMAIN`, `SYNTHETIC_DATA`, and `DATA_LAYER`. These are the mandatory G2.3 classification proof.
- **Native classification:** asynchronous Snowflake `SEMANTIC_CATEGORY` and `PRIVACY_CATEGORY` evidence from the optional classification profile. Enterprise Edition, privileges, object age, scheduling, and latency apply.

`043_bronze_classification_setup.sql` deliberately sets `auto_tag = false`; Snowflake recommendations are inspected without automatically translating every native category into the project taxonomy. Empty immediate results mean pending/not observed, not success.

## 10. Audit Proof

For one anchor, show:

```sql
SELECT PAYMENT_ID, _INGESTION_RUN_ID, _SOURCE_FILE_NAME,
       _SOURCE_FILE_ROW_NUMBER, _SOURCE_FILE_CONTENT_KEY,
       _SOURCE_FILE_LAST_MODIFIED, _STAGE_SCAN_TIME, _INGESTED_AT
FROM TRUSTED_AI_GOVERNANCE.BRONZE.PAYMENT_RAW
WHERE PAYMENT_ID = 'PAY_DEMO_001';
```

Use the run ID to retrieve the ten source-level run rows and file evidence. Capture the common `TRACE_ID`, executing role, counts, statuses, and timestamps. Access History is native delayed evidence rather than a synchronous success condition; the project tables close the immediate Bronze correlation gap without duplicating raw sensitive values.

Re-execution uses Snowflake COPY load history and `FORCE = FALSE`; already loaded unchanged files are not silently duplicated. `OVERWRITE = FALSE` protects stage upload. A future controlled replay requires a reviewed new path/file identity and explicit evidence—never a default force, delete, or truncate operation.

## 11. Interview Narrative

“We deliberately start governance at Bronze because waiting for curated data leaves the highest-risk raw layer uncontrolled. Each synthetic source is registered before loading, and every Bronze row carries the originating source, staged filename, row number, content key, scan time, run ID, and ingestion time. Business values stay source-preserving strings, so known defects remain visible rather than disappearing through premature type conversion. Snowflake-native classification and Access History complement project tags and run/file evidence; neither is overstated when asynchronous or edition-dependent. Least-privilege roles separate ingestion, stewardship, tag administration, restricted reading, and audit. The next Silver boundary can therefore validate and quarantine defects with complete provenance instead of guessing where they came from.”
